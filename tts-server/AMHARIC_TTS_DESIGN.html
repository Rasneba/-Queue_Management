Amharic TTS API — Architecture, Gap Analysis & Phased Plan to Replace Edge-TTS With Your Own Model

This document maps the implemented tts-server (FastAPI + Edge-TTS + Amharic-first normalization + lexicon + MP3/WAV/FLAC + web panel), evaluates Edge-TTS against Amharic requirements, and gives a detailed, actionable recommendation for replacing it with a self-hostable Amharic TTS with trade-offs, data, training, inference, cost, risks and a phased rollout.

1. Executive Summary

Your implementation is production-lean: deterministic normalization (numbers, IDs, dates, currency, %, phone, acronyms, orthography), gender×age mapping, styles/prosody, lexicon, downloads + player, and robust segment filtering (prevents “No audio was received”). The main blocker to full Amharic phonetic control is Edge-TTS’s closed G2P (gemination, ፀ/ጸ/ጠ/ተ, ሀ/ኀ/ሐ).

Keep (Strengths)
  • Normalization + prosody are yours (portable)
  • Low ops, no GPU required, works now
  • Clean API, test panel, cache, WAV/FLAC
  • Segment-level resilience + 400 for unspeakable text
Pain Points (Edge-TTS)
  • Closed phoneme/G2P → cannot force gemination/ሀ–ኀ–ሐ
  • Only 2 Amharic voices; age = rate/pitch only
  • Oromo male fallback (English)
  • Cloud-dependent, region/availability, no offline air-gapped
  • Hard to fine-tune per speaker/domain/accent
Recommendation (short)
  • Phase 0 (Now): Keep Edge-TTS, add a backend interface
  • Phase 1 (1–2 weeks): MMS-TTS (facebook/mms-tts-amh) as a baseline/benchmark — cheap on CPU but CC-BY-NC (non-commercial)
  • Phase 2 (6–10 weeks): Train your own VITS on licensed Amharic audio — the commercially shippable path
  • Phase 3 (optional): Zero-shot (F5-TTS / FishSpeech / Orpheus / Zonos) for per-request voice cloning
Key takeaway: Treat normalization+lexicon+prosody as your permanent “text front-end” (portable). Swap only the TTS backend (engine) behind synth_mp3/prepare via an interface to avoid breaking API/contracts.

Request Flow (Happy Path)
  1. POST /speak → validate (Pydantic), build cache key
  2. pick_voice(lang,gender,age) + age tuning (rate/pitch deltas)
  3. prepare(text,req) → normalize_for_speech(...) (normalization + prosody, drops unspeakable)
  4. synth_mp3(segments,...) calls Edge-TTS per segment (with pause prefix ።*n or ፚ handled), retries (3x), concat MP3
  5. convert(mp3,fmt) → WAV/FLAC via soundfile (24kHz mono PCM_16)
  6. Return audio bytes + headers (+ warnings if segments skipped)
Key Implementation Notes
  • Deterministic front-end: normalization + lexicon + prosody are engine-agnostic (keep this on swap)
  • Resilient: has_speech() strips Ethiopic/punct/whitespace; drop_unspeakable() carries pending pauses to next speakable segment; returns 400 “No speakable content found…” instead of 500
  • Signed prosody: uses +0%/+0Hz (fixes Edge signed-value edge cases)
  • ID expansion order: _expand_ids() before generic number expansion (fixes P-42)
  • Whole-token question detection: avoids false ፧ (e.g. ስማንያ)
  • Security: binds 127.0.0.1 by default (override TTS_HOST), CORS open, no auth (harden before external exposure)

3. Edge-TTS Analysis (Strengths, Weaknesses, Fit for Amharic)

Edge-TTS is pragmatic and high-availability today. For Amharic phonetics (gemination, glottal/velar fricatives, script-specific pronunciation) it’s a black box (Microsoft’s neural G2P + vocoder).

Strengths
  • Excellent SSML-lite prosody (rate/pitch/volume), low latency, stable
  • No local GPU required, CPU-light, easy to call
  • Natural intonation for many languages, segment streaming works
  • MP3 native, simple integration, reliable in CI/local
  • Zero training/hosting infra today
Weaknesses / Limitations
  • Closed G2P/phonemes: cannot force true gemination, distinguish ፀ/ጸ/ጠ/ተ, ሀ/ኀ/ሐ reliably at phoneme level
  • Voice inventory: 2 Amharic neural voices only; age = emulated (rate/pitch)
  • Coverage: Oromo male fallback to English
  • Offline/air-gapped: requires Microsoft endpoint (cloud-dependent). Terms/availability can change
  • Customization: no per-speaker fine-tune, no domain lexicon baked at phoneme level, no voice cloning control, no local model export
  • Determinism/quotas: transient NoAudioReceived/ConnectionTimeout possible (handled with retries + segment skipping)
  • PII/data residency: synthesis calls leave your machine to Microsoft (policy-dependent for prod)

4. Path to Your Own Amharic TTS (Detailed)

Goal: self-hostable (CPU or GPU), keep your text front-end (normalizer+lexicon+prosody), swap backend behind a small TTS interface. Below are practical model families, data, G2P, runtimes, trade-offs and hardware.

4.2 G2P / Phonemizer (Control Over Pronunciation)

To fix ፀ/ጸ/ጠ/ተ, ሀ/ኀ/ሐ, gemination you need explicit phoneme/grapheme mapping (especially for non-dictionary words). Your lexicon + normalization remain first pass.

Tool Type Status/Amharic Notes
HornMorpho FST morphological analyzer/generator Strong (Amharic/Tigrinya/Oromo) Best for morphology (roots/stems), can inform G2P/lemma; useful to disambiguate ሀ/ኀ/ሐ, verb forms
Custom rule-based G2P (Ethiopic) Rules + lexicon High control, maintainable Combine with pronunciation.json + exception list; deterministic, offline
eSpeak-NG Phonemizer Partial/varies Check Amharic rules; often needs extension
Phonemizer (backends: espeak/segments) Library Pluggable Good abstraction if you later train phoneme-based models (FastSpeech2)
Recommendation: Keep grapheme-based end-to-end models (VITS/MMS/F5-TTS) first — they learn G2P implicitly and avoid maintaining a brittle Amharic phoneme set. Move to explicit phonemes only if you hit consistent pronunciation errors after fine-tuning.

4.4 Inference Runtimes, Export, Deployment

Export Targets (Smaller/Faster)
  • ONNX: CPU-first, cross-platform, small (MMS-TTS ideal). Tools: torch.onnx.export, optimum, onnxsim
  • ONNX Runtime (ORT): CPU/GPU, threads, session options, low latency
  • GGUF (llama.cpp family): Relevant for LLM-TTS (Orpheus) via llama.cpp/vllm-style or kokoro/orpheus GGUF builds
  • TensorRT/DirectML/CoreML: GPU/edge acceleration if needed
Serving Options
  • FastAPI + local Python: simplest, drop-in behind current /speak
  • Triton Inference Server: batching, concurrency, model versioning (GPU fleet)
  • Coqui/TTS server, API wrapper: small microservice
  • Docker: reproducible (CPU image small for MMS-ONNX)
  • Windows/Linux: matches current win32 dev + prod Linux

4.5 Backend Abstraction (Swap Without Breaking API)

Keep prepare(...), normalize_for_speech, /normalize, lexicon, cache, formats exactly as-is. Introduce a TTS backend interface. 

tts-server/
  tts_backends/
    base.py        # Protocol: synth_segments(segments, voice_cfg, volume) -> (audio_bytes, warnings)
    edge_tts_backend.py     # MP3 out, no preprocessing
    mms_backend.py          # 16kHz WAV out, needs uroman romanisation first
    vits_backend.py         # your own model, 24kHz WAV out, no romanisation
    f5tts_backend.py        # zero-shot, needs speaker reference
  romanize.py     # uroman wrapper (only for MMS-class backends)
  config.py        # TTS_BACKEND=edge|mms|vits|f5tts
server.py          # inject backend (env TTS_BACKEND)
Benefit: A/B switch via env (TTS_BACKEND), feature flag per environment, instant rollback to Edge-TTS if regression.

5. Recommendation (Concrete & Phased)

Best balance: preserve your Amharic text IP (normalizer/lexicon), gain phonetic control + offline + on-prem, minimize risk and compute.

Primary Recommendation: MMS-TTS (facebook/mms-tts-amh) as the benchmark — then train your own VITS to ship
  • Why it is still the right first step: native Amharic, pretrained, CPU-excellent, small (36.3M params; ONNX export ~200–400 MB), fully offline, and it gives you a concrete quality/latency number to beat before you spend GPU time.
  • Two hard constraints, verified from the model card:
    (a) CC-BY-NC 4.0 — non-commercial, so it cannot ship in a paid product.
    (b) input must be romanised with uroman before it reaches the model; feeding Fidel script directly produces garbage. This adds a step your Edge-TTS backend does not need.
  • Therefore: use MMS to establish the evaluation harness, the backend interface and the latency budget — then fine-tune your own VITS on your own licensed Amharic audio. That model is commercially yours, works directly on Fidel text with no uroman step, and can be trained to fix exactly the gemination / ፀ/ጸ/ጠ/ተ / ሀ/ኀ/ሐ errors you care about.
  • Hardware: MMS benchmarking needs only 2–4 CPU cores and 2–4 GB RAM — no GPU. Own-VITS training is the first step that needs a GPU.

5.3 Evaluation Plan (Before Swapping Prod)

Objective (Intelligibility)
  • ASR-based: synth → wav2vec2-large-xlsr-53-amharic (or speechbrain) → CER/WER vs original
  • Focus on numbers, IDs, dates, phone (critical)
Subjective (Naturalness)
  • Blinded A/B: Edge vs MMS vs VITS (5–10 listeners)
  • MOS (1–5) per category (announcements, free text)
Robustness
  • Mixed Latin/Amharic, acronyms, punctuation-only guard
  • Long sentences, rare words, question marks (፧)
  • Queue cases (CARD-102, P-42)
Non-Functional
  • Latency/RTF, CPU/RAM, cold start, concurrency
  • Offline air-gapped, Windows stability, cache hit rate
Gate to production: A/B parity (or +0.1 MOS) on your top 50 real prompts + 100% pass on critical cases (numbers/IDs/queue) before flipping default backend.

Final Recommendation Summary:

  2. Phase 1 (baseline only). MMS-TTS (facebook/mms-tts-amh) — but it is CC-BY-NC 4.0 (no commercial use) and requires uroman romanisation first. Use it to get numbers, not to ship.
